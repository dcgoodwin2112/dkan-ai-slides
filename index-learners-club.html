MCP fundamentals · why it exists

The N×M problem

Every AI client × every data source used to be a bespoke integration. MCP replaces that grid with one protocol.

  • MCP — Model Context Protocol. A standard way for an AI application to discover and use another system's capabilities.
  • One line: "the USB-C port for AI tools." Implement the port once; any client plugs in.

An open standard — born at Anthropic, now under the Linux Foundation.

MCP fundamentals · the shape of it

Host, client, server

AI application
the host ⇄ MCP client
one per connection ⇄ MCP server
what you build ⇄ your system
DKAN, an API, files…
  • The host is the AI app (Claude Code, an IDE, a chat UI); it holds the model and runs the agent loop.
  • The server exposes capabilities. It has no AI model in it — it just answers requests.
  • Hosts usually run several servers at once — the model sees all their tools merged into one list.
Tools, Resources, Prompts · Drupal AI Learners Club · Aug 2026
Narrate the agent loop rather than showing it: your question plus the tool list go to the model, the model asks for a tool call, the host executes it, the result goes back to the model — repeat until it can answer. Under the hood it's JSON-RPC 2.0, but you rarely write protocol code — SDKs (TypeScript, Python, PHP…) handle it.
MCP fundamentals · how they connect

Two transports, same protocol

stdio

The host launches the server as a local child process and talks over stdin/stdout.

e.g. Claude Code ↔ drush dkan-mcp-server:serve

Streamable HTTP

The server is a remote endpoint — POST /mcp — with real auth (OAuth bearer tokens).

e.g. a browser app ↔ a DKAN site

Same messages, same tools, same behavior — the transport is plumbing, not semantics. You'll see both today: Claude Code over stdio, MCP Dojo over HTTP.

MCP fundamentals · the full picture

Three more primitives — running the other way

MCP also defines three client-side primitives. These flip the arrow: the server initiates, the client answers.

Sampling

The server asks the client to run a model call — borrowing the host's LLM instead of shipping its own.

Elicitation

The server asks the human for structured input mid-operation — confirm, fill in a form, or cancel.

Roots

The client tells the server what's in scope — which locations it should work within.

Two are as old as MCP itself; elicitation arrived mid-2025. Client support is only now catching up.

Today we build on the server three — they're what you implement first, and what the demo shows.

Tools, Resources, Prompts · Drupal AI Learners Club · Aug 2026
Detail for Q&A: sampling (sampling/createMessage) sends messages + model preferences; the host runs them through its own model with human oversight — a server gets LLM power with no API key of its own. Elicitation (elicitation/create, added in the June 2025 spec revision) carries a flat JSON schema the client renders as a form; responses are accept / decline / cancel. Roots (roots/list) are URIs — classically file:// project directories — with a change notification. Sampling and roots shipped with the first spec (Nov 2024) — what's new is clients actually implementing them; adoption lagged the spec for years. DKAN-flavored examples: sampling = the server summarizing a dataset with *your* model; elicitation = update_dataset asking you to confirm fields before committing; roots = scoping an agent to one catalog. Server primitive 1 of 3 · model-controlled

Tools

{
  "name": "search_datasets",
  "description": "Search datasets by keyword
    via the DKAN search API, with pagination.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "keyword":  { "type": "string" },
      "page":     { "type": "integer", "minimum": 1 },
      "pageSize": { "type": "integer", "maximum": 50 }
    },
    "required": ["keyword"]
  },
  "annotations": { "readOnlyHint": true }
}
  • A tool = name + description + JSON Schema for input (and optionally output)
  • Annotations hint at behavior: read-only, destructive, idempotent, open-world
  • They feed the host's "Allow this tool call?" prompt — the human-in-the-loop gate you've seen in Claude Code
The description is written for the model, not for humans. It's the only thing the model reads when deciding whether and how to call your tool. Write it like documentation for the model — because it is.
Tools, Resources, Prompts · Drupal AI Learners Club · Aug 2026
This JSON is the real wire shape of a real tool from the DKAN server — the same one we'll call in the demo. "Description is a prompt" gets its payoff in the demo's description-sandbox flourish: rewrite it to "DEPRECATED AND BROKEN" and the model stops calling it. Annotations are hints for the host, not enforcement. Dark side if asked: a malicious server can steer the model the same way (tool poisoning / prompt injection) — only connect to servers you trust; the host's permission prompts are the real gate. Server primitive 2 of 3 · app-controlled

Resources

Data the application (the host app) puts in front of the model — the model didn't ask.

  • Each resource has a URI — dkan://dataset/cedcd327-… — and a MIME type
  • Templates parameterize them: dkan://dataset/{id}, with typeahead completion for the variables
  • The app can read one (just look) or attach it to the conversation's context

Think: "open this record in the conversation" — the way an IDE attaches a file, a catalog attaches a dataset.

Tools, Resources, Prompts · Drupal AI Learners Club · Aug 2026
The hardest primitive for newcomers because nothing happens without an app that uses them — which is exactly why the demo matters: preview vs. attach, then open the context inspector and show the attached dataset sitting in the system prompt. Tools = the model pulls; resources = the app pushes.
Server primitive 3 of 3 · user-controlled

Prompts

Reusable, parameterized workflows the human invokes — the server's slash commands.

  • Server-authored: the people who know the data encode how to work with it — /explore_dataset, /dataset_health_check
  • Arguments with completion — the client renders them as a form or inline typeahead
  • The server expands the slash command into full message text — shown to the user before it sends, so nothing reaches the model unseen

A prompt is expertise, shipped with the server — the difference between handing someone a toolbox and handing them a checklist.

Tools, Resources, Prompts · Drupal AI Learners Club · Aug 2026
DKAN ships five: find_datasets, explore_dataset, build_datastore_query, dataset_health_check, diagnose_harvest. The demo's two-Enter flow (first Enter previews the expansion, second sends) is the teaching moment — nothing reaches the model without the user seeing it first.

Applied · the use case

Why open data is a natural fit

Governments publish data open by default — policy since a 2013 executive order, law since the OPEN Government Data Act (2019).

FAIR — findable, accessible, interoperable, reusable — written for machines as much as people.

But "published" ≠ "answered" — the answer is in a 12-million-row CSV somewhere, behind a query language most people will never learn.

Data that's already machine-actionable — exactly the shape MCP serves well.

The compressed version of the DrupalCamp talk's opening arc. Precision if asked: Executive Order 13642, "Making Open and Machine Readable the New Default for Government Information" (May 2013); the OPEN Government Data Act is Title II of the Evidence Act (Jan 2019). The FAIR line to say out loud: open data spent a decade making itself machine-actionable — MCP is the machine finally showing up.

Two halves: Metastore & Datastore

Metastore

The records describing the data. CRUD over metadata (DCAT, the standard open-data metadata format): titles, descriptions, distributions, schemas.

→ tells you what exists.

Datastore

The rows themselves, made queryable via the DatastoreQuery endpoint.

→ lets you compute on it.

The MCP tools discover through the metastore and answer through the datastore.

Applied · the one code slide

One tool = one attribute plugin

#[Tool(
  id: 'search_datasets',
  description: new TranslatableMarkup(
    'Search datasets by keyword via the
     DKAN search API, with pagination.'),
  inputSchema: [ /* JSON Schema */ ],
  readOnly: TRUE, destructive: FALSE,
)]
final class SearchDatasetsTool extends SearchToolBase {

  public function execute(array $arguments,
    ClientGateway $gateway): mixed {
    return $this->search->searchDatasets(
      (string) ($arguments['keyword'] ?? ''),
      (int) ($arguments['page'] ?? 1),
      (int) ($arguments['pageSize'] ?? 10),
    );
  }

}
  • The #[Tool] attribute is the wire definition from the JSON slide — same name, description, schema, annotations
  • execute() is thin: it forwards to a plain Drupal service (dkan_query_tools)
  • Base classes supply DI + defaults; logic stays testable outside the protocol

Pattern to name: thin adapters over framework-neutral services, so the same logic also powers DKAN's chat-widget module. "Write the description like a prompt" — it's the exact string the model reads.

Applied · design for agents

Designed for a caller that pays per token

  • Row caps everywhere: ≤500 datastore, ≤100 metastore, ≤50 search
  • Truncated descriptions; heavy fields dropped; the expensive catalog read cached
  • Sanity flags (row_cap_hit, zero_rows) mark partial answers honestly
Errors come back structured.

An unknown_column error carries available_columns — the agent fixes itself in one turn. The error lands in the tool result, where the model can read it.

The client pays too: every connected tool's schema rides along on every model call. Watch the context-growth meter in the demo.

Three things to take home

  1. MCP is three primitives and a lifecycle — small enough to learn in an afternoon, and now you have.
  2. Who controls what is the load-bearing idea: tools = model, resources = app, prompts = user.
  3. Descriptions are prompts — write yours like documentation for the model, and treat other people's as an attack surface: only connect to servers you trust.
